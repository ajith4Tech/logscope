# Logscope

Centralized Kubernetes (k3s) log collection. **Vector** runs as a DaemonSet, tails
every container log, classifies severity, and writes **infra** vs **per-namespace**
files — or ships the same classified lines to S3. S3 objects are keyed by
severity only (`<key_prefix root>/<severity>/%Y/%m/%d/…`), **not** by scope;
Falco events are the one exception (`…/security/<severity>/…`, see below). The
web app derives infra vs namespace from each line's namespace.

Clone the repo, copy `config.example.yaml` → `config.yaml`, set your node path and
namespaces, render, deploy. No code changes.

## How configuration works

Identity and classification live in **one YAML file**. `scripts/render.py` writes
cluster install files into `deploy/` (Helm values, namespace, backup CronJob,
raw `vector.yaml`).

**Why a Python pre-processor (not Vector env templating)?** Vector 0.57+ disables
`${ENV}` interpolation in its config by default, and even with it enabled it
could not build VRL from a namespace glob list, a line-format template, or a
keyword table. So `render` writes literal values into the config (S3 bucket and
region included; the `AWS_REGION` / `S3_BUCKET` env vars it also sets are not
read by the config). AWS keys still come from the environment, read by Vector's
AWS SDK, not by interpolation. Helm already `tpl`s `customConfig`, which is
why file-sink paths use `{{`{{ scope }}`}}`. A small render step keeps one
source of truth. Cost: Python 3 + PyYAML before `helm upgrade`. Alternative
would be a hand-maintained Vector config per cluster.

Environment variables override YAML after load (`LOGSCOPE_CLUSTER_NAMESPACE`,
`LOGSCOPE_PATHS_HOST_PATH`, `LOGSCOPE_S3_BUCKET`, … — full list in
`scripts/render.py` `ENV_MAP`). `LOGSCOPE_CONFIG` selects the file.

## Line format (default = current behavior)

```
<timestamp> - <namespace> - <pod>/<container> - <message>
```

Same wrapping for Prometheus `# HELP` / `# TYPE` / samples. Change
`format.line` / `format.metrics` in config for a tagged layout later — that is a
config edit, not a Vector rewrite.

## Layout (file sink)

```
<host_path>/
├── logs/infra/{error,warning,info,debug,metrics}.log
├── logs/namespaces/<ns>/{error,warning,info,debug,metrics}.log
├── logs/security/{error,warning,info,debug}.log   # Falco (scope=security)
├── logs/security.log                              # every Falco event again (file kit only)
└── backups/current/          # incremental mirror (CronJob)
```

Infra namespaces default to `default`, `kube-public`, `kube-node-lease`,
`kube-system` (globs allowed, e.g. `kube-*`).

## Deploy (node-local files)

```bash
pip install -r requirements.txt
cp config.example.yaml config.yaml   # then edit paths.host_path, routing, etc.

# Directory must already exist on the node (hostPath type: Directory).
sudo mkdir -p /var/lib/logscope

# Generates deploy/namespace.yaml, deploy/values-{local,agent}.yaml,
# deploy/vector.yaml and deploy/backup-cronjob.yaml from config.yaml.
# These hold your real config and are gitignored — never commit them.
logscope render                    # or: make render / python3 scripts/render.py

kubectl apply -f deploy/namespace.yaml
helm repo add vector https://helm.vector.dev && helm repo update
helm upgrade --install vector vector/vector -n logging \
  -f deploy/values-local.yaml --version 0.57.0
kubectl -n logging rollout status ds/vector

kubectl apply -f deploy/backup-cronjob.yaml
kubectl apply -f local-vector/test-job.yaml   # -> logs/namespaces/vector-demo/
```

If GitHub chart downloads time out:

```bash
helm upgrade --install vector ~/.cache/helm/repository/vector-0.57.0.tgz \
  -n logging -f deploy/values-local.yaml
```

Do not remove the `vector.dev/exclude=true` label on the install namespace
(the `deploy/namespace.yaml` generated by `logscope render` sets it) or Vector will scrape itself.

Internal metrics: `kubectl -n logging port-forward ds/vector 8686:8686`

## Production (S3)

Same `config.yaml`. Set `sinks.s3.enabled: true`, `sinks.s3.region`,
`sinks.s3.bucket` (examples only in `config.example.yaml` — never real account
values). Optionally `sinks.file.enabled: false` if you do not want node files.
Re-render, then follow [`production-vector/README.md`](./production-vector/README.md).

**Credentials.** Without `sinks.s3.irsa_role_arn`, Vector reads
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` from the Kubernetes Secret named
by `sinks.s3.secret_name` (default `vector-s3-creds`) in `cluster.namespace`.
[`deploy/k3s/s3-secret.example.yaml`](./deploy/k3s/s3-secret.example.yaml)
creates it: its `metadata.name` must equal `sinks.s3.secret_name`. The web app
(and `logscope s3-lifecycle`, unless given `--secret`) read the keys from the
file `deploy/k3s/s3-secret.yaml` itself (whatever its `metadata.name`), else
from `AWS_*` env / the default AWS chain.

**S3 retention** (`sinks.s3.retention_days`, default 30): after setting it in
`config.yaml`, run once:

```bash
logscope s3-lifecycle          # or: python3 scripts/apply_s3_lifecycle.py
# uses deploy/k3s/s3-secret.yaml when present, else AWS_* env / default chain;
# LOGSCOPE_S3_* overrides apply, exactly as for render
```

That installs a native S3 Lifecycle expiration rule (rolling by object age under
Logscope’s `key_prefix` root). It is a **bucket property**, not a Vector or
Helm setting — separate from `render.py` and DaemonSet deploy. Changing
`retention_days` later requires re-running this script; editing `config.yaml`
and redeploying Vector alone does **not** update the live rule.

## Classification

The first rule that sets a bucket wins, in this order (rules are
`severity.buckets` in config):

1. structured level field (`severity.structured_fields`), mapped through each
   bucket's `level_equals` / `level_contains`;
2. a level embedded in the raw line: JSON `"level":"…"` (`json_level_keys`),
   then logfmt `level=…` (`logfmt_level`);
3. klog prefixes: `E####` and `F####` (fatal) → error, `W####` → warning,
   `I####` → info (`klog:` per bucket, a letter or a list);
4. Prometheus exposition shape → the bucket with `prometheus: true`;
5. `severity.extra_patterns` (regex → bucket);
6. keywords (`keywords:` per bucket);
7. `severity.default` (`info`).

Then the **Falco override**: for Falco's own containers (see below) scope
becomes `security`, the message becomes Falco's `output`, and Falco's
`priority` replaces the bucket via `falco.priority_map`.

## Multiline aggregation

Without multiline, stack traces and multi-line Postgres errors are scraped
**one physical line at a time**. Continuations (`File "…"`, `DETAIL:`, `HINT:`,
…) get their own timestamps, often land in the wrong severity file, and are
painful to grep as a single incident.

Logscope fixes that with a Vector `reduce` transform (on by default). A line
**starts a new event** only when `.message` matches a known start pattern —
ISO-8601 timestamp, klog `E`/`W`/`I`/`F` prefix, JSON `{…}`, logfmt `level=`,
or a closed set of severity words (`INFO` / `WARN` / `WARNING` / `ERROR` /
`FATAL` / `DEBUG` / `TRACE` / `CRITICAL` / `PANIC` followed by `:`). Everything
else is treated as a **continuation** of the previous event for that
pod/container and is concatenated before classification.

Before (fragmented Postgres error — each line a separate event):

```
ERROR:  duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(alice@example.com) already exists.
HINT:  Use ON CONFLICT DO UPDATE to merge the row.
STATEMENT:  INSERT INTO users(email) VALUES ('alice@example.com')
```

After (one event; newlines flattened to spaces in the flat line format):

```
… - ERROR:  duplicate key … DETAIL:  Key (email)=… HINT:  … STATEMENT:  INSERT …
```

Configure under `multiline` in `config.yaml` (`enabled`, `starts_when`,
`timeout_ms`). Default is **enabled**. `group_by` is
`pod_name` + `container_name` + `pod_namespace`, so concurrent pods/containers
never merge into each other’s events. CRI split-line merge remains on via
`auto_partial_merge`.

## Security events (Falco)

Logscope does **not** bundle or manage Falco’s ruleset. Falco is a separate
[official Helm chart](https://github.com/falcosecurity/charts) install. When
`falco.enabled` is true, Vector recognizes Falco’s **own pod stdout** already
flowing through the existing `kubernetes_logs` source (JSON lines: `output`,
`priority`, `rule`, `time`, `output_fields`). There is **no additional Vector
source**.

Classification (config-driven): a line is Falco's when its pod is in
`falco.namespace` **and** its container is listed in `falco.containers`
(default `[falco]`, the official chart's container name). Other pods and
sidecars in that namespace (e.g. `falcoctl`) are classified like any other
workload.

- **scope** is set to `security` (even if that namespace would otherwise be
  infra or `namespaces/<ns>`).
- Falco `priority` is mapped through `falco.priority_map` to a Logscope
  severity bucket. Config validation fails if any of the eight official
  levels is missing from the map.
- The tagged line’s message is Falco’s `output` field (rule name prefixed
  when it is not already in `output`).

**File sink:** every Falco event is written to **both** `security.log` and
the mapped severity file under `logs/security/` (`error.log` / `warning.log` /
`info.log` / `debug.log`).

**S3:** every Falco event is written **once**, under
`<key_prefix root>/security/<severity>/…` (the `falco_security_s3` sink); the
main S3 sink leaves Falco events out. The web app reads Falco events from the
`security/` prefix only (lines tagged ` scope=security` found in a regular
prefix, written there by older versions, are skipped as duplicates).

Non-Falco events are unchanged. Set `falco.enabled: false` to skip this path
entirely; Falco-namespace logs then use normal classification.

Deploy Falco (not run by `scripts/render.py`):

```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
helm install falco falcosecurity/falco \
  -f deploy/k3s/falco-values.yaml -n falco --create-namespace
```

Values in [`deploy/k3s/falco-values.yaml`](./deploy/k3s/falco-values.yaml)
turn on JSON + stdout. Keep Helm `-n` / `namespaceOverride` in sync with
`falco.namespace` in config:

```yaml
falco:
  enabled: true
  namespace: falco          # which namespace Falco's own pods run in — used to detect Falco output
  containers: [falco]       # Falco's container name(s) in those pods
  priority_map:             # Falco priority scale -> Logscope severity buckets
    emergency: error
    alert: error
    critical: error
    error: error
    warning: warning
    notice: info
    informational: info
    debug: debug
```

## Backup

File-sink installs only. The CronJob copies the node-local log files
(`paths.host_path`, which must already exist on the node; its hostPath type is
`Directory`). With an S3-only pipeline (`sinks.file.enabled: false`),
`scripts/render.py` doesn't render it, because S3 and its lifecycle rule are
the store. A CronJob left over from an earlier file-sink install keeps failing
with `FailedMount`; remove it with
`kubectl -n logging delete cronjob vector-log-backup` once you confirm nothing
uses it.

Byte-append, not rsync: skip a source whose last byte is not newline; if the
backup is larger than the source, recopy; else append new bytes. Cadence is
`backup.schedule` (default `*/30 * * * *`).

```bash
kubectl -n logging create job --from=cronjob/vector-log-backup backup-manual
```

## Web app

`webapp/` is a log viewer with anomaly insights. It reads the S3 objects
Vector writes (same `config.yaml`) and caches them in SQLite. It ships as one
`logscope` command, as a standalone binary or a container image:

```
logscope serve        [--host H] [--port P] [--config FILE]   web app (UI + API)
logscope render       [-c FILE] [-o DIR]                      Vector Helm values / vector.yaml
logscope s3-lifecycle [-c FILE] [--secret FILE]               S3 retention rule
logscope db           [--db FILE] backup|verify|restore|compact [--state]
logscope healthcheck  [--port P]                              GET 127.0.0.1:$PORT/healthz; exit 0/1
logscope selfcheck    [--config FILE]                         FTS5, config, writable paths, AI/S3 settings (no network)
logscope version
```

From a source checkout the same commands run as `python3 -m logscope ...`
(or `pip install .`), and the older entry points still work
(`python3 -m webapp.api.server`, `python -m webapp.api.dbtool`,
`scripts/render.py`, `scripts/apply_s3_lifecycle.py`).

The log cache (SQLite, rebuildable from S3) defaults to
`$XDG_CACHE_HOME/logscope/cache.sqlite`, else `~/.cache/logscope/cache.sqlite`
(never `/tmp`); `webapp.backend.db_path` or `LOGSCOPE_WEBAPP_DB_PATH` override
it (the Helm chart keeps it on its PVC). Saved views, alerts and AI settings
live in a separate state database (`$XDG_DATA_HOME/logscope/state.sqlite`).
Every time filter, window and bucket uses each record's event time in UTC
epoch seconds (`ts_epoch`); a timestamp without a zone is taken as UTC, and a
line whose timestamp does not parse is placed at its S3 object's time and
counted in `/api/status` (`timestamp_fallbacks`). A cache from an older
version is backfilled in the background (`storage.ts_backfill` in
`/api/status` while it runs).

### API added since v0.3.0

Reads are open; "admin" means the `Authorization: Bearer <admin token>` header
(see the chart README). Cross-origin browser requests are refused for every
write.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET`, `PUT /api/settings/ai` | admin | AI provider, model, key (write-only), feature flags, budgets |
| `POST /api/settings/ai/test` | admin | One minimal call with the saved settings |
| `GET /api/settings/ai/usage?days=N` | admin | Calls, tokens and estimated cost per feature |
| `POST /api/anomalies/{id}/summarize` | — | AI summary of one anomaly (`tier`, `regenerate`, `skip_signature`) |
| `POST /api/ai/filters` | — | Natural language → proposed filters (nothing is applied) |
| `POST /api/ai/feedback` | — | 👍/👎 on a cached answer (`X-Logscope-Client` header) |
| `GET`, `POST /api/alerts/channels` | POST: admin | Notification channels (URLs are write-only) |
| `PATCH`, `DELETE /api/alerts/channels/{id}` | admin | Change or delete a channel |
| `POST /api/alerts/channels/{id}/test` | admin | Send a test notification |
| `GET`, `POST /api/alerts/rules` | POST: admin | Alert rules with their live status and the ingest watermark |
| `GET`, `PATCH`, `DELETE /api/alerts/rules/{id}` | PATCH/DELETE: admin | One rule |
| `POST`, `DELETE /api/alerts/rules/{id}/mute` | — (rate limited) | Mute (`duration` or `until`) / unmute |
| `GET /api/alerts/events?rule=&state=&since=&cursor=&limit=` | — | Transition history with delivery status (`sent`, `queued`, `retrying`, `failed_final`, `superseded`) |
| `POST /api/alerts/events/{id}/retry` | admin | Retry a queued or failed notification now |
| `POST /api/alerts/backtest` | — | Replay a rule over up to 7 days of history |

Alert notifications are delivered durably: one that no channel accepts is
retried after 30 s, 1, 2, 5, 10 and 30 min, then hourly for up to a day
(then `failed_final`); retries survive restarts, and an older firing
notification is dropped (`superseded`) once a newer transition of the same
rule and group was delivered.

### AI cost

AI is optional (`webapp.ai.provider`: `openrouter`, `gemini`, `openai` or
`anthropic`; anything else, e.g. `none`, leaves it off), and most requests
never reach a provider. Every explanation
(one line, the filtered logs, an anomaly) is answered by the cheapest source
first. The UI shows which one answered and how old the answer is:

1. **Signature**: about 40 built-in known patterns, such as OOMKilled,
   CrashLoopBackOff, image pull errors, probes, DNS, TLS, ENOSPC, PostgreSQL
   errors, Go/Python/Java crashes and the common Falco rules
   (`webapp/api/signatures.yaml`). These answers are free. Click **Ask AI
   anyway** for a model answer instead. You can add your own rules under
   `webapp.ai.signatures` (same format). They are validated at startup,
   including that every command is a supported read-only kubectl
   diagnostic.
2. **Cache**: answers are stored per log template, which is the message
   with numbers, ids, IPs, timestamps, pod hashes and so on replaced. A
   second pod or IP with the same error reuses the answer. Answers are kept
   for 7 days (`webapp.ai.cache_ttl_hours`) and survive restarts.
   - **Regenerate** asks the AI again.
   - 👎 drops the cached answer.
3. **AI**: one call with a compact input. Filtered explanations and anomaly
   summaries send the top 15 templates with counts and 3 redacted exemplars,
   not raw lines (about a third of the tokens on the test fixture).
   - Identical requests in flight share one call.
   - The static prompt comes first, so provider prompt caching applies
     (Anthropic `cache_control`; OpenAI and Gemini cache the stable prefix
     implicitly).
   - **Deep analysis** uses `deep_model`, with its own cache and its own
     `daily_calls.deep_analysis` budget.

Anomalies show a free template summary: what changed, counts against the
baseline, top templates and the matching signature. The AI summary runs on
click. With the `anomaly_auto_summary` flag on (default off), anomalies at or
above `webapp.ai.auto_summary_min_urgency` (default `urgent`) are summarized
by a background queue. The queue runs 2 workers and batches up to 5 anomalies
per call. Over budget, a batch is dropped. Anomaly detection never waits for
the queue.

**Zero-cost option: a local model.** Any OpenAI-compatible server on
`localhost` works, for example [Ollama](https://ollama.com) (`ollama serve`,
`ollama pull llama3.1:8b`). In Settings, or in config, set:

```yaml
webapp:
  ai:
    provider: openai
    model: llama3.1:8b
    base_url: http://localhost:11434/v1   # http is allowed only for localhost
    prices: {"llama3.1:8b": {input: 0, output: 0}}   # optional: shows $0 instead of "unknown"
```

A local endpoint needs no API key. In Kubernetes, `localhost` means the
web app pod itself, so run the model as a sidecar or add its Service host to
`ai.allowedHosts` (that requires https). Small local models give weaker
troubleshooting plans than hosted ones. The usage panel shows each source's
share (AI calls, cache hits, signature hits) and the token cost.

### Binary

One self-contained file per architecture (PyInstaller; Python and all
dependencies inside). Built on Debian bookworm; its newest glibc symbol is
GLIBC_2.35, so it runs on Ubuntu 22.04+, Debian 12+ and RHEL 10 (not RHEL 9).
Download it from a GitHub release
(verify against `sha256sums.txt`) or build it with Docker:

```bash
make bin                                   # -> dist/logscope-<version>-linux-<arch> (+ .sha256)
install -m 0755 dist/logscope-*-linux-amd64 /usr/local/bin/logscope
logscope selfcheck --config /etc/logscope/config.yaml
logscope serve --config /etc/logscope/config.yaml   # http://127.0.0.1:8000
```

[`deploy/systemd/logscope.service`](./deploy/systemd/logscope.service) is an
example unit (hardened, state in `/var/lib/logscope`, credentials in a mode
0600 `EnvironmentFile`).

### Container image

`Dockerfile` builds the binary (onedir) on `python:3.12-slim-bookworm` and
copies it into `gcr.io/distroless/cc-debian12`: no shell, no package manager,
UID 10001, both bases pinned by digest, Python dependencies installed from
`requirements.lock` with `--require-hashes`.

```bash
make image                     # current arch, loaded into the local Docker
make smoke                     # build image + binary and run the smoke checks
make image-multi PUSH=1 IMAGE=ghcr.io/<owner>/logscope   # amd64 + arm64, SBOM + provenance, pushed
make scan                      # trivy, if installed
```

The image tag is the version without its leading `v` (`v0.3.0` -> `0.3.0`;
untagged commits use `git describe`, e.g. `828a417-dirty`). `INCLUDE_KUBECTL=true`
adds a pinned, checksum-verified `kubectl` for clusters that enable actions
(see the chart's `kubectl.*` / `rbac.*` values). The version is reported by
`logscope version`, `/api/status` (`version`) and the `X-Logscope-Version`
response header.

### k3s: import or registry

- **Single node, no registry:** build on the node (or copy the image there)
  and import it into k3s's containerd. `make k3s-import` prints the command:

  ```bash
  docker save ghcr.io/<owner>/logscope:<tag> | sudo k3s ctr images import -
  helm upgrade --install logscope deploy/helm/logscope -n logging -f $V \
    --set image.repository=ghcr.io/<owner>/logscope --set image.tag=<tag> --set image.pullPolicy=Never
  ```
- **Multi-node:** an imported image exists on one node only. Push it to a
  registry every node can reach (`make image-multi PUSH=1`, or the release
  workflow on a `v*` tag pushes to GHCR), set `image.repository` (and
  `image.digest` to pin it), and `image.pullSecrets` if the registry is private.

Vector (`timberio/vector`) and Falco keep running from their upstream images;
only the web app uses this image. Deploying the chart is described in
[`deploy/helm/logscope/README.md`](./deploy/helm/logscope/README.md).

- Running suggested `kubectl` steps from the UI is off unless you start the
  server with `LOGSCOPE_ACTIONS_ENABLED=true` (they run with your kubeconfig;
  the API has no authentication).
- The server answers only to trusted `Host` names: IP addresses, `localhost`
  and the `--host` name. Reach it by any other name? Add it to
  `LOGSCOPE_TRUSTED_HOSTS` (comma-separated; `*.example.com` allowed).
- Back up the SQLite cache with `logscope db backup <file>` (see the chart
  README for restore).
